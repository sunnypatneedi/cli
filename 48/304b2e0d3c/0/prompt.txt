// ── Bar chart component ──
function BarChart({ data, valueKey, labelKey, maxWidth = 200, color = colors.green }) {
  const max = Math.max(...data.map(d => d[valueKey]));
  return (
    <div style={{ display: "flex", flexDirection: "column", gap: 4 }}>
      {data.map((d, i) => (
        <div key={i} style={{ display: "flex", alignItems: "center", gap: 8, fontFamily: "monospace", fontSize: 13 }}>
          <span style={{ color: colors.textMuted, width: 40, textAlign: "right" }}>{d[labelKey]}</span>
          <div style={{ flex: 1, display: "flex", alignItems: "center", gap: 8 }}>
            <div style={{
              height: 16,
              width: max > 0 ? `${(d[valueKey] / max) * 100}%` : 0,
              minWidth: d[valueKey] > 0 ? 4 : 0,
              background: color,
              borderRadius: 2,
              transition: "width 0.3s ease",
            }} />
            <span style={{ color: colors.textMuted, fontSize: 12, whiteSpace: "nowrap" }}>
              {d[valueKey]}{valueKey === "hours" ? "h" : ""}
            </span>
          </div>
        </div>
      ))}
    </div>
  );
}

# Rigorous Thinking Protocol

A methodology for dismantling conventional wisdom and arriving at robust conclusions through evidence people already have in front of them.

## Core Principle

**Not theoretical arguments, just: look at what actually happens.**

The goal is not to win arguments but to force examination of held beliefs against observable reality. Conclusions become robust when they survive genuine attempts at falsification.

---

## The Protocol

### Phase 1: Construct Strongest Counterarguments

Before accepting any thesis, generate the strongest possible objections:

1. **Steelman, don't strawman** - Make each counterargument as strong as an intelligent defender would make it
2. **Aim for 5-8 genuine objections** - If you only find 2-3, you haven't thought hard enough
3. **Include objections you don't believe** - Your job is to test the thesis, not defend it
4. **Name the specific mechanism** - "This might fail because X causes Y" not "this seems risky"

**Quality check:** Would an intelligent critic say "yes, that's exactly my concern"?

---

### Phase 2: Point to Evidence Already Available

For each counterargument, identify observable evidence that tests it:

**The key question: "What would we expect to see if this objection were true?"**

Evidence types (in order of strength):
1. **Natural experiments** - Identical situations with one variable changed (e.g., twin studies)
2. **Base rate data** - What actually happens across many instances (not cherry-picked examples)
3. **Revealed preferences** - What people do vs. what they say
4. **Time-delayed outcomes** - What happens when constraints are removed
5. **Multi-child/multi-instance observation** - Variance within controlled conditions

**Bad evidence:**
- Anecdotes that confirm the desired conclusion
- Expert opinions without falsifiable predictions
- Theoretical models without empirical validation
- Outlier examples (Tiger Woods, Serena Williams) without base rate context

---

### Phase 3: Close Escape Hatches

When an objection seems to survive, probe deeper:

**Causal direction questions:**
- "Does A cause B, or does B cause A, or does C cause both?"
- "What would happen if we intervened on A directly?"

**Selection bias questions:**
- "Who is missing from this sample?"
- "Why are we only seeing the survivors?"

**Counterfactual questions:**
- "If this factor mattered, what else would we expect to see?"
- "What's the control group?"

**Base rate questions:**
- "For every success case, how many failures used the same approach?"
- "What percentage of the population does this apply to?"

---

### Phase 4: Track What Collapses vs. What Stands

After each round of evidence examination, update explicitly:

**Collapses completely:**
- [Objection] - doesn't hold because [specific evidence]

**Weakened but uncertain:**
- [Objection] - less confident because [evidence], but still possible if [condition]

**Still stands:**
- [Objection] - evidence is [ambiguous/lacking/supports the objection]

**Don't rush to collapse objections.** The goal is genuine updating, not capitulation or stubbornness.

---

### Phase 5: Identify Asymmetries

Most robust insights reveal asymmetric relationships:

**Common asymmetries:**
- **Upside/downside asymmetry:** Easy to destroy, hard to create
- **Necessary vs. sufficient:** Required but not enough
- **Individual-specific bands:** What varies by person/context vs. what's universal
- **Threshold effects:** Below X nothing works, above X diminishing returns

**Questions to surface asymmetry:**
- "Can A create B, or can A only prevent not-B?"
- "Does the same intervention have different effects on different people?"
- "What's the shape of the relationship? Linear? Threshold? Diminishing?"

---

### Phase 6: Prevent Premature Agreement

**If the user/interlocutor agrees too quickly, push back:**

# Algorithm Selection Guide (v2)

## 0) 20-Second Intake Checklist

Before picking anything, answer these quickly (even implicitly):

1. **Exact vs approximate?**
   - If user-facing and errors are costly → approximate only as a gate (verify downstream).

2. **Streaming vs batch?**
   - Streaming + bounded memory → sketches/digests/samplers.

3. **Need deletions?**
   - If yes → Cuckoo (membership), otherwise rotate time-buckets (Bloom/CMS).

4. **Need merge across shards/time windows?**
   - HLL / CMS / TDigest are designed to merge well.

5. **What's the keyspace size (n) and error tolerance (p, ε, δ)?**

6. **Latency constraints?**
   - High QPS lookup → Bloom/Cuckoo/Trie/HNSW.

**If you don't know, assume:**
- Approx OK for analytics dashboards
- Approx as gate + verify for UX-critical flows

## 3) Parameter Sizing & Tuning Cheat-Sheet

This is what usually blocks "algorithm picking" in practice.

### Bloom Filter (membership gate)

**Inputs**: expected insertions `n`, desired false-positive rate `p`.

```
Bits:           m = -(n × ln p) / (ln 2)²
Hash functions: k = (m / n) × ln 2
```

**Rules of thumb:**
- `p = 1%` is usually fine for non-UX-critical gates (analytics, caching).
- `p = 0.1%` or lower for UX flows where false positives "hide" content.

**Operational trick**: If you need "delete", rotate filters by time bucket (daily/weekly) and check multiple buckets.

---

### HyperLogLog (unique counts)

Relative standard error is roughly:
```
RSE ≈ 1.04 / sqrt(m)  where m = 2^p registers
```

**Rules of thumb:**
- `p=12` (4096 regs) → ~1.6% RSE
- `p=14` (16384 regs) → ~0.8% RSE

**Use `p=14` as a strong default** unless memory is extremely tight.

---

### Count-Min Sketch (frequencies)

**Guarantee**: estimated count ≤ true count + ε·N with probability (1 − δ)

```
Width: w = ceil(e / ε)
Depth: d = ceil(ln(1/δ))
Memory ≈ w × d counters
```

**Defaults:**
- For "trending queries/books": `ε = 0.001`, `δ = 0.01` is a common starting point.
- Always keep a candidate heap + optional exact counter map for top ~100 to verify/rerank.

---

### MinHash + LSH (set similarity)

**Key knobs:**
- `numHashFunctions` (k) controls signature quality.
- `bands` (b) controls candidate recall/precision.
- Rows per band `r = k / b`.

**Candidate probability for similarity s:**
```
P(candidate) = 1 - (1 - s^r)^b
```

**Defaults:**
- `k = 128`, `b = 32` (so `r = 4`) is a good baseline.
- If too many candidates → increase `r` (fewer bands), or reduce `b`.

---

### T-Digest (quantiles)

**Knob**: compression (often called `δ`).

**Defaults:**
- `δ ~ 100` for general p50/p95.
- `δ ~ 200–500` if you care about p99/p99.9 tails.

---

### Trie (autocomplete)

The "algorithm" is easy; the trick is memory + relevance.

**Defaults:**
- Normalize keys (lowercase, trim, ASCII-fold if needed).
- Store top-K IDs per node (K=5–20) to avoid traversing huge subtrees.
- Consider Radix-style compression later if memory hurts.

---

### HNSW (vector nearest neighbors)

**Knobs:**
- `M` (graph degree) → recall vs memory
- `efConstruction` (build quality)
- `efSearch` (query-time recall/latency)

**Defaults:**
- `M = 16`
- `efConstruction = 200`
- `efSearch = 50` (fast) up to `200` (higher recall)

**Memory gut-check:**
```
Embedding storage dominates: n × dims × 4 bytes (float32)
Example: 1M vectors × 1536 dims × 4B ≈ 6GB just for vectors
```

Plan early for: float16, quantization, or fewer dims if scale is large.

## 4) Composition Recipes (How You Actually Ship)

### Trending Dashboard (fast + bounded memory)

```
Count-Min Sketch to track frequencies
  → maintain Heap top-K of candidates
  → (optional) verify/re-rank top candidates with exact counts in DB/cache
```

**Why**: CMS gives you "good enough" candidates cheaply; exact verification avoids CMS collisions driving UI.

---

### "Already Recommended" (membership with rollback)

```
Cuckoo Filter per user/session (or per user-day bucket)
  → fallback store for "must be correct" items (DB/cached set)
```

**Why**: deletions and bounded memory, but still needs a correctness safety net for UX-critical cases.

---

### Search UX (layered)

```
Prefix suggestions: Trie (fast typing)
Full query results: BM25
Semantic fallback / "similar meaning": HNSW (embeddings)
```

This "layered search" avoids trying to make one tool do everything.

---

### Similar Readers / Similar Families

```
Represent each family as a set of book IDs (or liked items)
  → MinHash + LSH to find similar sets
  → use overlaps to generate recommendations
```

If you move to embeddings later, swap in HNSW for the retrieval stage.

## 5) Anti-Patterns (Expanded)

| Don't do this | Do this instead | Why |
|---------------|-----------------|-----|
| Use Bloom filter as a "truth source" | Bloom as a gate, verify on positives | False positives are real |
| Use CMS numbers directly as ranking | CMS → candidates → exact verify | CMS collisions overestimate |
| Use HLL for small exact counts | Exact set for small n, HLL after threshold | HLL bias/noise can dominate |
| Use Reservoir Sampling for stable A/B assignment | Deterministic hashing for assignment | Reservoir is for sampling streams |
| Put raw user input straight into hashes | Canonicalize keys first | Normalization bugs destroy accuracy |
| Store all user IDs to count unique | HyperLogLog | 99% memory savings |
| `SELECT * WHERE title LIKE '%query%'` | BM25 Index | Relevance ranking, faster |
| `SELECT COUNT(*) GROUP BY` for trending | Count-Min Sketch | Real-time, bounded memory |
| Compare all pairs for similarity | MinHash + LSH | O(n) vs O(n²) |
| pgvector exact k-NN for recommendations | HNSW | 50-100x faster |
| Store all items to compute percentiles | T-Digest | Streaming, bounded memory |

# Rigorous Thinking Protocol

A methodology for dismantling conventional wisdom and arriving at robust conclusions through evidence people already have in front of them.

## Core Principle

**Not theoretical arguments, just: look at what actually happens.**

The goal is not to win arguments but to force examination of held beliefs against observable reality. Conclusions become robust when they survive genuine attempts at falsification.

---

## The Protocol

### Phase 1: Construct Strongest Counterarguments

Before accepting any thesis, generate the strongest possible objections:

1. **Steelman, don't strawman** - Make each counterargument as strong as an intelligent defender would make it
2. **Aim for 5-8 genuine objections** - If you only find 2-3, you haven't thought hard enough
3. **Include objections you don't believe** - Your job is to test the thesis, not defend it
4. **Name the specific mechanism** - "This might fail because X causes Y" not "this seems risky"

**Quality check:** Would an intelligent critic say "yes, that's exactly my concern"?

---

### Phase 2: Point to Evidence Already Available

For each counterargument, identify observable evidence that tests it:

**The key question: "What would we expect to see if this objection were true?"**

Evidence types (in order of strength):
1. **Natural experiments** - Identical situations with one variable changed (e.g., twin studies)
2. **Base rate data** - What actually happens across many instances (not cherry-picked examples)
3. **Revealed preferences** - What people do vs. what they say
4. **Time-delayed outcomes** - What happens when constraints are removed
5. **Multi-child/multi-instance observation** - Variance within controlled conditions

**Bad evidence:**
- Anecdotes that confirm the desired conclusion
- Expert opinions without falsifiable predictions
- Theoretical models without empirical validation
- Outlier examples (Tiger Woods, Serena Williams) without base rate context

---

### Phase 3: Close Escape Hatches

When an objection seems to survive, probe deeper:

**Causal direction questions:**
- "Does A cause B, or does B cause A, or does C cause both?"
- "What would happen if we intervened on A directly?"

**Selection bias questions:**
- "Who is missing from this sample?"
- "Why are we only seeing the survivors?"

**Counterfactual questions:**
- "If this factor mattered, what else would we expect to see?"
- "What's the control group?"

**Base rate questions:**
- "For every success case, how many failures used the same approach?"
- "What percentage of the population does this apply to?"

---

### Phase 4: Track What Collapses vs. What Stands

After each round of evidence examination, update explicitly:

**Collapses completely:**
- [Objection] - doesn't hold because [specific evidence]

**Weakened but uncertain:**
- [Objection] - less confident because [evidence], but still possible if [condition]

**Still stands:**
- [Objection] - evidence is [ambiguous/lacking/supports the objection]

**Don't rush to collapse objections.** The goal is genuine updating, not capitulation or stubbornness.

---

### Phase 5: Identify Asymmetries

Most robust insights reveal asymmetric relationships:

**Common asymmetries:**
- **Upside/downside asymmetry:** Easy to destroy, hard to create
- **Necessary vs. sufficient:** Required but not enough
- **Individual-specific bands:** What varies by person/context vs. what's universal
- **Threshold effects:** Below X nothing works, above X diminishing returns

**Questions to surface asymmetry:**
- "Can A create B, or can A only prevent not-B?"
- "Does the same intervention have different effects on different people?"
- "What's the shape of the relationship? Linear? Threshold? Diminishing?"

---

### Phase 6: Prevent Premature Agreement

**If the user/interlocutor agrees too quickly, push back:**

- "Don't try to please me. Think hard about what I've said."
- "It's okay to disagree still. Be rigorous."
- "What objections do you still have?"

**If you (Claude) agree too quickly, pause:**

- "Let me think through this more rigorously..."
- "I agreed quickly, but let me steelman the opposing view..."
- "What am I still missing?"

The conclusion is only robust if it survives genuine pushback from both sides.
